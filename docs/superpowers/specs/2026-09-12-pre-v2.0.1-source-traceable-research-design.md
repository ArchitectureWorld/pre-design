# Pre 2.0.1 可查数据源与分析链设计

日期：2026-09-12
目标分支：`feat/pre-v2.0.1`
正式基线：`main@49140423e14f3d3abcf3815c9bdf68e8e5e26730`（Pre V2.0.0 已合并进入 main）。

## 1. 目标

把现有 57 项专业工作流升级为一条可查、可复核、可重算的数据链：

```text
项目正式资料 / 官方网站 / 官方开放数据 / 权威行业数据 / 专业计算
→ ResearchStep
→ EvidenceRecord
→ 标准化 / 交叉核验
→ 确定性汇总与计算
→ AnalysisTrace
→ LLM 专业解释与综合
→ 独立 Evidence Validator
→ Project State
→ Report / Presentation
```

每个关键事实、指标和结论都必须回答：来源是什么、何时取得、原始位置在哪里、原始值是什么、如何清洗/汇总/计算、采用什么方法、最终结论依赖哪些证据、当前置信度和限制是什么。

## 3. 数据来源优先级

```text
P0 项目正式资料 / 实测数据
P1 政府、法定机构官方数据
P2 官方标准、政府认可专业公共数据
P3 权威行业数据库、专业机构公开数据
P4 地图 / POI / 市场平台等辅助数据
P5 LLM inference / assumption
```

P5 永远不能单独形成 `fact`。高风险事实至少需要 1 条 A 级证据；普通事实至少需要 1 条 A/B 级证据，或 2 条独立 B/C 级来源交叉验证。

**高风险只提高机器核验强度，不等于人工审批。** 风险等级用于提高证据等级、交叉核验强度、最低置信度和自动修订预算；不得因为 `risk=H` 自动转入人工确认。

## 4. 核心对象

### DataSourceCatalog

登记允许使用的数据来源：`sourceId / name / publisher / priority / authorityLevel / homepage / allowedDomains / accessModes / supportedDataKinds / freshnessPolicy / reliabilityGrade / notes`。

### WorkflowResearchSpec

每个 Workflow 对应一份可执行研究计划：`workflowId / requiredDataPoints / optionalDataPoints / preferredSources / queryTemplates / extractionRules / normalizationRules / researchSteps / aggregationMethod / analysisMethod / crossCheckRules / freshnessRules / minimumEvidence / fallbackPolicy / outputClaims`。

### ResearchStep

ResearchStep 负责把“网站清单”变成真正的上下级执行逻辑。每一步保存：

`stepId / order / title / dependsOnStepIds / dataPointIds / sourceIds / action / produces / notes`。

正式层级固定为：

```text
Chapter
→ Workflow
→ ResearchStep
→ DataPoint
→ DataSource
→ EvidenceRecord
→ Normalization / Aggregation / Deterministic Calculation
→ AnalysisTrace
→ OutputClaim
```

数据源只能挂在实际使用它的 ResearchStep 下。没有 ResearchSpec 的 Workflow 必须明确显示“待映射”，不得用通用网站清单伪装为已完成研究链。

### EvidenceRecord

真实采集记录：`evidenceId / workflowId / dataPointId / sourceId / sourceType / sourceUri / sourceTitle / publisher / publishedAt / capturedAt / asOf / locator / rawValue / normalizedValue / unit / contentHash / reliability / claimClass`。

### AnalysisTrace

结论分析链：`traceId / workflowId / claimId / inputEvidenceIds / inputObjectIds / methodId / methodVersion / parameters / calculationSteps / outputValue / confidence / limitations`。

## 6. 分析规则

- 事实型：采集 → 单位/时间/空间口径标准化 → 去重 → 交叉核验 → 指标。
- 对比型：统一指标口径与统计期 → 对比矩阵 → 差异 → 专业判断。
- 空间型：可信边界 + GIS/POI → 几何计算 → 距离/覆盖/密度 → 结论。
- 规模型：目标人群/需求 → 标准/基准 → 参数 → 公式 → 区间/敏感性 → 建议规模。
- 投资型：工程量 → 单价来源 → 基准日 → 税费/预备费 → 汇总 → CAPEX / 生命周期成本。

确定性计算不得由 LLM 心算产生。LLM 只负责解释、比较、综合和提出待验证假设。

## 7. Workflow 执行链

```text
Workflow READY
→ WorkflowResearchSpec
→ ResearchStep DAG
→ Workspace / Web / API / Professional Tool Provider
→ EvidenceRecord
→ Evidence Validator
→ Deterministic Aggregation / Calculation
→ AnalysisTrace
→ LLM State Candidate
→ Quality + Evidence Gate
→ auto_pass / auto_revise / blocked_external / quality_unresolved / evidence_conflict
→ Project State
```

其中：

- `auto_pass`：自动确认并继续；
- `auto_revise`：自动返工；
- `blocked_external`：外部资料不可取得，保持机器可见阻断，不自动索要人工审批；
- `quality_unresolved`：自动修订预算耗尽，保留问题与可追溯原因，不默认转人工；
- `evidence_conflict`：证据冲突未消解，保持冲突状态并继续执行不受影响的下游/并行任务；
- `needs_human` 仅保留给显式 manual/legacy 兼容路径，不属于 V2.0.1 automatic 模式的正常状态。

V2.0.1 的自动运行语义由 `2026-09-12-pre-v2.0.1-automation-policy-overlay-design.md` 约束，V0.6 历史合同中的人工复核字段不直接决定 automatic 模式行为。

## 9. 自动化与人工边界

V2.0.1 默认是端到端自动化：采集、核验、分析、自动返工、State 写入和 Gate 推进均由 DSH Runtime 完成。**人工不是流程推进器。**

人工主要用于：

- 用户主动查看后进行局部微调、偏好修改或覆盖某个结论；
- 现实世界确实只能由外部主体作出的业务选择，作为 `external decision input` 输入系统；
- 用户主动切换到 manual 模式。

以下情况不得被解释成“必须人工审批”：

- `risk=H`；
- 法定边界、投资、政策等高风险专业事项；
- 自动修订达到上限；
- Evidence 冲突；
- 外部数据暂时缺失。

这些状态应分别通过更严格的自动证据要求、确定性复算、更高置信度、更多自动修订，或 `blocked_external / quality_unresolved / evidence_conflict` 表达。用户如果愿意，可以在任何节点进行 override/edit；人工修改产生新 Revision，并由系统自动重算受影响的下游。

## 10. 实施阶段

### Phase A — Research Contract Foundation

建立 DataSourceCatalog、WorkflowResearchSpec、ResearchStep、EvidenceRecord、AnalysisTrace 的类型、JSON Schema、Registry、打包规则和测试；同时完成首批真实官方 Source Catalog 与 3 个代表性 Workflow Research Spec（项目认知、政策法定条件、投资估算）。

### Phase B — Real Providers

实现 Workspace Provider、官方 Web Search/Fetch Provider、公开 API Provider；保留 Provider 接口用于后续 GIS/BIM/造价等专业工具。

### Phase C — Evidence Validator + Deterministic Methods

实现来源等级、域名、时效、冲突、最小证据规则；引入确定性 aggregation/calculation 与 AnalysisTrace。风险越高，机器验证越严格，不增加默认人工审批点。

### Phase D — Runtime Integration

把真实 Evidence/Trace 注入 Workflow Analyzer；`auto_pass` 不再接受纯 Agent 自报，必须由独立 Evidence Validator 通过。Automatic Policy Overlay 负责确保通过后的 Workflow 与 Gate 自动推进。

### Phase E — 57 Workflow Coverage

57 项逐项完成“步骤顺序、查什么、去哪里查、如何提取、如何汇总、如何计算、如何核验、缺失怎么办、最终形成什么结论”，并用真实项目做端到端回归。

## 11. 验收标准

任取一个关键结论，系统必须可还原：Workflow、ResearchStep、来源网站或项目文件、DataPoint、数据时间、原始定位、原始值、标准化值、计算步骤、方法版本、输入证据、结论、置信度与限制。不能还原完整链路的结论不得进入完全可信的 `auto_pass`。

此外，任取一个 `risk=H` Workflow，只要证据、确定性计算和中央 Quality Gate 达标，就必须能够在 automatic 模式下自动确认并继续，不得因为风险等级本身要求人工审批。
