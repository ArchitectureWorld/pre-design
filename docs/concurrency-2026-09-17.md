# 五个子 Agent 并发与完成后补位

## 问题证据

正式少潭河会话原生产配置为最多三个工作项并发。`ParallelWorkflowExecutor` 先用 `Promise.all` 等整批分析（含质量/Schema纠正），再统一按合同顺序提交。空闲名额不能补任务，已完成的结果也不能立即解锁下游。恢复时又只选择 persisted running，未用剩余名额启动独立 ready 项。

只读运行证据：13:48 开始的 04.03 和 04.05 有约 117.883 秒模型请求重叠。但 04.03 于13:50:02完成，直到13:53:13才确认，额外等了190.512秒；04.05的三次业务纠正直到13:53:07结束。`work/cycle6-concurrency-live-audit.json` 保留脱敏时间表。此前部署暂停造成的空档不归因为调度故障。

## 本轮行为

用户明确要求将 DSH 子 Agent 并发上限扩至五个。生产 Host 配置和执行器上限均改为5；Codex的只读监督子 Agent仍只有一个。

- 自动协调器启用滚动执行，按当前 Ready Set 填满可用名额。
- 每个工作项的研究、模型分析和有界纠正占一个名额；结果完成后即校验、串行提交，随后解锁下游并补位。
- 所有中央提交、Revision/CAS、工作流转换及自动Gate仍由同一写入循环依次完成。
- 依赖必须已确认后才能启动。上限是容量，不保证任意阶段都能运行五项；现有57项依赖图中很多阶段只能运行一至两项，有一个层级可运行五项。
- 同一执行窗口内按workflowId去重，恢复中的工作项与独立ready项共享五个名额。
- 暂停关闭当前协调器代次的派发许可，已启动任务自然结束；立即恢复先等待旧代次结束，旧代次异常不能吞掉恢复请求或修改新代次状态。
- 业务阻断停止继续补位，但成功的已启动同批任务仍提交。基础设施异常先等待已经启动的模型结束，再交给协调器记录故障。
- 模型路由、已有120次任务授权及持久预算预留规则均未改变。

`runReadyBatch` 的直接调用仍默认只处理一个有界初始窗口；生产协调器显式启用 `refill: true`。这保留单批测试/调用方语义，并让正式自动执行持续补位。

## 回归与审查

新增9项滚动调度回归，验证5并发/超额配置限制、完成即补位、依赖提交前禁止启动、恢复补位、串行写入、暂停排空、业务阻断、基础设施异常排空。增加一个暂停立即恢复且旧批次失败的回归。旧“必须按合同顺序等待提交”断言改为“按完成顺序串行提交”。

首轮新调度测试5失败1通过，修复后通过。监督子 Agent发现暂停恢复竞态，新测试先失败再修复；32项针对测试通过，监督内存复现由starts=1恢复为starts=2，且无错误工作流写入。全量回归和正式部署证据追加至 `docs/supervision-2026-09-17.md`。
